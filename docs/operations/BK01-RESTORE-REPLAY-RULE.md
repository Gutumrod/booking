# BK01 — กฎ Restore → Replay Deletion (ข้อมูลที่ลบแล้วห้ามกลับมา)

**สถานะ:** ก่อนขาย — **ข้อกำหนดบังคับ** (ยังไม่มีกลไกในระบบ) · **เอกสารเท่านั้น ไม่มี SQL ไม่มีสคริปต์รันกับฐานจริง**
**ที่มา:** `STATUS-HOUSE.md` Addendum A-27 ข้อ 8 (backup 60 วัน · หลัง restore ต้อง replay deletion tombstone) · Owner "ตามนี้" 2026-10-02
**ใช้คู่กับ:** `docs/operations/BACKUP_RESTORE_RUNBOOK.md` (ขั้น restore) · `BK01-DATA-DELETION-RUNBOOK.md` (§6/§7)

---

## 0. หลักการเดียวที่ต้องจำ

> **การลบไม่ได้ลบย้อนหลังเข้าไปใน backup.**
> ถ้า restore แล้วเปิดระบบทันที ข้อมูลที่ลบไปแล้วจะ **กลับมามีชีวิต** ซึ่งผิดทั้งต่อคำขอของลูกค้าและต่อนโยบายของเรา
> ⇒ **หลัง restore ทุกครั้ง ต้อง replay รายการที่ลบไปแล้วทับก่อนเปิดให้ผู้ใช้เข้าถึง**

ความครบของข้อมูลหลัง restore **ไม่ใช่สัญญาณว่าปลอดภัย** — มันคืออาการของปัญหา

---

## 1. ขอบเขตที่บังคับ

บังคับใช้กับ **ทุกครั้ง** ที่นำข้อมูลกลับจาก backup/PITR แล้วจะเปิดให้ผู้ใช้เข้าถึง ไม่ว่า:

- restore ทั้งฐานจาก catastrophic recovery
- restore บางตาราง/บางร้าน
- กู้ไฟล์ storage (`deposit-slips`) กลับมา
- ทำ restore rehearsal บนสำเนา **ก่อน** ตัดสิน cutover (ต้องซ้อมกฎนี้ด้วย ไม่ใช่ซ้อมเฉพาะ restore)

ข้อมูลสำรองเก็บ **60 วัน** หลังปิดบัญชี (A-27 ข้อ 8) ⇒ หน้าต่าง replay คือ **ตั้งแต่หลังวันที่ของ backup จนถึงเวลาที่เปิดระบบ**

---

## 2. สรุปขั้นตอนบังคับ (ทำตามลำดับ)

1. **หยุดการเปิดให้บริการ** — ระบบต้องอยู่ในสถานะที่ผู้ใช้ยังเข้าถึงข้อมูลไม่ได้ระหว่างขั้นตอนนี้ (maintenance/hold)
2. **นำ deletion tombstone / deletion log** ที่บันทึกไว้ **ตั้งแต่หลังวันที่ของ backup** มาทับ (replay)
   ⇒ รายการที่ถูกลบไปแล้วต้องไม่มีข้อมูลกลับมาให้ผู้ใช้เห็น **ไม่ว่ากรณีใด**
3. **ต้องมีที่เก็บ tombstone แยกจากฐานข้อมูลที่ restore มา** (tombstone ต้องไม่ถูก restore ทับ)
   ⇒ **ถ้ายังไม่มีที่เก็บนี้ ห้ามเปิดระบบ และรายงานเป็น blocker**
4. **ยืนยันผลด้วยคนที่สอง** แล้วจดในบันทึกการลบว่า replay อะไรไป จำนวนเท่าไร ตรวจอะไรแล้ว
5. **ห้ามใช้ "ข้อมูลที่ restore มาดูครบ" เป็นเหตุผลให้ข้ามข้อนี้**

**รายละเอียดและลำดับเต็มของการ restore:** `docs/operations/BACKUP_RESTORE_RUNBOOK.md` (ข้อ "Restore procedure")
— กฎนี้เป็น **ข้อเพิ่มที่ต้องรันก่อน "Authorize cutover"** ของ runbook นั้น

## 4. Checklist: restore → replay → cutover

ทำเครื่องหมายทุกข้อ · **ข้อ 1–7 ต้องครบก่อน "Authorize cutover"**

- [ ] 1. ประกาศ incident/hold และ **หยุดให้ผู้ใช้เข้าถึง** ข้อมูล
- [ ] 2. ระบุ recovery point + ช่วงข้อมูลที่จะหาย (ตาม `BACKUP_RESTORE_RUNBOOK.md`)
- [ ] 3. restore เข้าเป้าหมายที่แยกก่อน (ถ้าทำได้)
- [ ] 4. ตรวจ schema + tenant invariants
- [ ] 5. ตรวจร้าน/การจอง/subscription/audit/สลิปตัวแทน (ตาม runbook)
- [ ] 6. **Replay deletion tombstone/log** ตั้งแต่หลังวันที่ของ backup — ทับรายการที่ลบไปแล้วทั้งหมด
- [ ] 7. **ยืนยันด้วยคนที่สองว่าไม่มีข้อมูลที่ลบแล้วกลับมา** (ตรวจตัวอย่างจริง ไม่ใช่เชื่อตามรายงาน)
- [ ] 8. **ที่เก็บ tombstone ไม่ได้ถูก restore ทับ** (ยืนยันแยกจากฐานที่ restore)
- [ ] 9. reconcile Stripe/provider state หลัง DB recovery
- [ ] 10. **Authorize cutover** (เฉพาะเมื่อ 1–9 ผ่าน)
- [ ] 11. production smoke test + บันทึกข้อมูลที่หายจริง/deviation
- [ ] 12. จดบันทึก: replay อะไรไป จำนวนเท่าไร ใครตรวจ ใครอนุมัติ (Runbook §7)

**ถ้าข้อ 6 หรือ 8 ทำไม่ได้ ⇒ หยุดที่ข้อ 8 และรายงาน blocker — ห้าม cutover**

## 5. Rehearsal (ซ้อม)

- [ ] ซ้อม **restore + replay** หนึ่งรอบบนข้อมูลจำลอง/สำเนา **ก่อนเปิดขาย** และ **ทุกไตรมาส** (ตาม `BACKUP_RESTORE_RUNBOOK.md`)
- [ ] ซ้อมต้องพิสูจน์: ลบข้อมูลตัวอย่าง → ทำ backup → restore → replay → **ข้อมูลที่ลบไม่กลับมา**
- [ ] เก็บบันทึกผลซ้อม (วันที่/ขั้นตอน/ผู้ทำ/ผู้ตรวจ/ผล)
- [ ] ซ้อม **ก่อน** ประกาศว่าระบบรองรับกฎนี้

## 6. บันทึกความไม่แน่ใจ

- กฎนี้เขียนจาก A-27 ข้อ 8 (Owner "ตามนี้" 2026-10-02) — **ระยะ 60 วันของ backup เป็นคำตัดสินของ Owner** ยังต้องสอดคล้องกับข้อความกฎหมายที่ผ่านทนาย
- **กลไก deletion tombstone ยังไม่มีในระบบวันนี้** — เอกสารนี้เป็นข้อกำหนด/สัญญา ไม่ใช่คำอธิบายระบบที่ทำงานแล้ว
- เอกสารนี้ไม่ให้ SQL/สคริปต์รันกับฐานจริง · ตัวอย่างทั้งหมดเป็นข้อความอธิบาย
- การซ้อมจริงต้องรอที่เก็บ tombstone (B7) — จนกว่าจะมี **ยังซ้อมพิสูจน์ไม่ได้**
