## 3. กฎเหล็ก: `booking` ที่มีเหตุการณ์เงิน (`deposit_money_events`) ห้าม DELETE — ทำ anonymize เท่านั้น

`local_service.deposit_money_events` อ้าง `bookings`/`shops` **แบบไม่ cascade** + มี trigger ห้ามแก้
(ผลตรวจโค้ดผู้คุม; A-27 "ผลตรวจโค้ด") ⇒ **ห้าม `DELETE` แถว `bookings` หรือ `shops` ที่มีเหตุการณ์เงินผูกอยู่ ทุกกรณี**

- ถ้าลบ → FK จะทำให้คำสั่งล้มเหลว
- ถ้าดัดแปลง FK/trigger ให้ผ่าน → ทำลายหลักฐานการรับเงิน
- ทางเดียวที่ใช้ได้: **anonymize ข้อมูลระบุตัวตน** — **ชื่อ · เบอร์โทร · URL สลิป** — ทับด้วยค่าที่ไม่ระบุตัวตน แล้วคงโครง FK ไว้ครบ
- `deposit_money_events` **ไม่ลบรายแถว** เก็บตลอดอายุบัญชีร้าน และให้ร้านส่งออกก่อนปิดบัญชี (A-27 ข้อ 3)
- **วันนี้ BK01 ยังไม่มีฟังก์ชัน anonymize** ⇒ ถ้างานต้องลบ booking ที่มีเหตุการณ์เงิน ให้ **ระงับไว้ + ส่งต่อ** (ไม่ทำ UPDATE ด้วยมือบนฐานที่ใช้งานร่วม)

**ตัวอย่างเชิงข้อความ (อธิบายเจตนา — ห้ามรัน ไม่ใช่สคริปต์):**
```
ความตั้งใจ: เขียนทับ customers.name / customers.phone และ bookings.slip_url
ด้วยค่าไม่ระบุตัวตน (เช่น __deleted__<id>) โดย "ไม่" แตะแถว deposit_money_events
เงื่อนไข: ต้องมาจากฟังก์ชัน anonymize ที่ผ่าน scope + รีวิวเท่านั้น — ไม่มีในระบบวันนี้
ห้าม: DELETE bookings ที่มี deposit_money_events · ปิด trigger · UPDATE มือบน production
```
สัญญาที่ต้องมีก่อนทำได้จริง: [[OWNER INPUT: House-owned scope R1 (anonymize) ผ่านสัญญากับ Codex]]

## 4. ขั้นตอนทีละข้อ

### 4.1 ลบตามคำขอของร้าน (ร้านสั่ง — WSTERA เป็น Processor)

1. Pre-flight §2 ครบ
2. **แยก Records เป็นสามกองก่อนแตะข้อมูล**

   | กอง | ความหมาย | การกระทำ |
   | --- | --- | --- |
   | ลบได้ | ไม่ผูกหลักฐานที่ต้องเก็บ | ลบ |
   | anonymize | ต้องเก็บโครง/บัญชี แต่ไม่ต้องรู้ว่าเป็นใคร | ทำให้ไม่ระบุตัวตน (§3) |
   | ต้องเก็บ | กฎหมาย/ข้อพิพาท/บัญชีบังคับ | เก็บ + แจ้งร้านตามจริงว่าทำไม |

3. **Dry-run ก่อนเสมอ** — ดูรายการ + เหตุผล `deletable` / `kept` (รูปแบบ "ดูตัวอย่าง → ยืนยัน → ลบ" ใช้เป็นแบบอย่างได้จาก `previewRetentionCleanup` ใน `apps/booking-admin/src/lib/ticket-service.ts`)
4. **สลิปมัดจำ:** ใช้ `scripts/cleanup-stale-deposit-slips.mjs` เท่านั้น — dry-run เป็นค่าเริ่มต้น · **ไม่ลบสลิปที่ผูกกับ booking ทุกกรณี** · ต้องระบุ `--min-age-hours` ทุกครั้ง (ไม่มี default โดยเจตนา) · ตัวเลขต้องมาจาก A-27 ข้อ 3 (12 เดือน)
   ```
   ตัวอย่างเชิงข้อความ (ห้ามรันบน production โดยไม่ผ่าน scope ที่รีวิวแล้ว):
   node scripts/cleanup-stale-deposit-slips.mjs --shop <shopId> --min-age-hours 8760
   → ดูผล dry-run → ให้คนที่สองรีวิว → ค่อยรันด้วย --confirm-plan <sha256> ที่รีวิวแล้ว
   ```
5. **คนที่สองยืนยันก่อนลบจริง**
6. **อย่ารวมหลายกลุ่มข้อมูลในรอบเดียว** — แยกกลุ่มเพื่อกู้คืนได้ถ้าพลาด
7. แจ้งร้านเมื่อเสร็จ ตามช่องทางที่อนุมัติ

### 4.2 ลบตามคำขอของลูกค้าปลายทาง (data-subject request)

1. Pre-flight §2 ครบ · บันทึกใน `BK01-PRIVACY-REQUEST-INTAKE.md` log แล้ว
2. **ข้อมูลลูกค้าของร้าน = ร้านเป็น Controller** ⇒ โดยหลัก **ส่งต่อคำขอให้ร้านวินิจฉัย** เว้นแต่ Owner สั่งเป็นอย่างอื่น — [[OWNER INPUT: นโยบายส่งต่อคำขอของลูกค้าปลายทางให้ร้าน (ผู้ควบคุมข้อมูล) และกรณีที่ WSTERA ดำเนินการเอง]]
3. ถ้า WSTERA ดำเนินการ (ตามคำสั่งร้าน): ทำข้อ 4.1 ข้อ 2–7
4. ส่งคำยืนยันให้ผู้ขอตามช่องทางที่อนุมัติ — ร่างนี้ **ไม่สัญญาระยะเวลาตอบกลับ** จนกว่าจะยืนยัน: [[OWNER INPUT: ระยะเวลาตอบกลับคำขอใช้สิทธิ์ที่ทนาย/Owner อนุมัติ]]

### 4.3 ลบ/เก็บเมื่อร้านเลิกใช้

## 5. Legal Hold Override — ตรวจก่อนลบ **ทุกครั้ง**

1. ตรวจว่ามี hold ไหม: ข้อพิพาท/ข้อร้องเรียนที่ยังไม่ยุติ · คิวระหว่างคืนมัดจำ · การสอบสวนความปลอดภัย · คำขอหน่วยงานรัฐ/กระบวนการทางกฎหมาย · รอบบัญชียังไม่ปิด
2. **มี hold หรือไม่แน่ใจ ⇒ "เก็บ" และหยุดรายการนั้น** (เกณฑ์กำกวมนำไปสู่ "เก็บ" เสมอ)
3. ระงับ**เฉพาะ**ข้อมูลที่เกี่ยวกับ hold นั้น ไม่ระงับทั้งชุด
4. ผู้ปลด hold = [[OWNER INPUT: ผู้มีอำนาจอนุมัติ/ปลด Legal Hold (ชื่อบทบาท) ที่ Owner กำหนด]]
5. จดทั้งกรณี "ระงับ" และ "กลับเข้ากระบวนการ" — ใครปลด เมื่อไร
6. วันนี้ยังไม่มีระบบ hold อัตโนมัติ — เป็น manual และต้องยืนยันกับ Owner/บัญชี/สนับสนุน · **ห้ามสมมติว่าไม่มี hold**

## 10. บันทึกความไม่แน่ใจ

- ตัวเลข retention ทั้งหมดคัดจาก A-27 (Owner "ตามนี้" 2026-10-02) **ไม่ใช่ข้อสรุปทางกฎหมาย** และยังไม่ผ่านทนาย/บัญชี
- การอ้าง FK/trigger ของ `deposit_money_events` มาจากผลตรวจโค้ดผู้คุมใน A-27 (ไฟล์ P0 ไม่ได้อยู่ใน worktree นี้) — ก่อนใช้คำสั่งจริงต้องยืนยันกับ DDL จริง
- เอกสารนี้ไม่ให้คำสั่ง SQL/สคริปต์ที่รันกับฐานจริง · ตัวอย่างทั้งหมดเป็นข้อความอธิบายเจตนา
- กลไกใน §6 (tombstone) ยังไม่มีในระบบวันนี้ — เขียนเป็นข้อกำหนด ไม่ใช่คำอธิบายระบบที่ทำงานแล้ว
