## 0. ทำไมต้องมีคู่มือนี้ และทำไมยังใช้ไม่ได้ทันที

วันนี้ BK01 **ยังไม่มีกลไกลบข้อมูลอัตโนมัติ** ที่ครอบคลุม `bookings`, `customers`, `line_users`,
`line_notification_logs` และไฟล์สลิปใน storage — ฟังก์ชันลบที่มีอยู่มีเพียง
`delete_closed_tickets_before` (ตั๋วที่ปิดแล้ว) และ `delete_shop_holiday` เท่านั้น
ส่วน `request_account_closure` เป็นเพียงการ INSERT คำขอลงตาราง `account_closure_requests`

ผลที่ตามมา และเป็นเหตุผลที่คู่มือนี้มีสถานะ "ร่าง":

1. ข้อความกฎหมายที่ลูกค้าเห็นระบุระยะเวลาเก็บข้อมูลบางรายการเป็น `[[OWNER INPUT: …]]`
   อยู่ และระบุไว้ชัดว่า 60 วันใช้กับ "ข้อมูลสำรองหลังการปิดบัญชี" เท่านั้น
   — ถ้าเราเปิดขายพร้อมข้อความที่ล็อคตัวเลขไว้ แต่ไม่มีกลไกลบจริง ลูกค้าจะถือว่ามีกลไกที่ไม่มีอยู่
   ซึ่งเป็นปัญหาสัญญาและ PDPA ไม่ใช่ปัญหาความสวยงามของข้อความ
2. **อัปเดต 2026-10-02:** Owner ระบุตัวเลขชุดแรกเป็นลายลักษณ์อักษรว่า "ตามนี้"
   (`vault/06-Agent-Logs/WSTERA-House/STATUS-HOUSE.md` Addendum A-27) ⇒ ข้อ 3 เติมตัวเลขได้แล้ว
   **แต่ทั้งฉบับยังเป็นร่าง**: ข้อ 3/6/7 ยังต้อง **ทนาย/บัญชียืนยัน** และตัวเลขนี้ยังห้ามนำไป

   จะผ่านการตรวจ
3. คู่มือนี้ไม่กำหนดตัวเลขเอง — ทุกตัวเลขในข้อ 3 คัดจาก A-27 ตรงตัว พร้อมกำกับที่มาทุกช่อง

## 2. หลักการที่ห้ามละเมิด (เรียงตามความสำคัญ)

1. **สลิปที่ผูกกับ booking ต้องไม่ถูกลบระหว่างที่ยังระงับข้อพิพาทได้** — สลิปคือหลักฐานการชำระ
   ของลูกค้า การลบสลิปคือการทำลายใบเสร็จระหว่างช่วงที่ยังโต้แย้งได้
2. **หลักฐานทางบัญชี/ภาษีมีเอกเทศเหนือคำขอของลูกค้า** — ถ้ากฎหมายกำหนดให้เก็บ ให้เก็บ และ
   แจ้งลูกค้าตามความเป็นจริง ห้ามลบแล้วเงียบ
3. **หลักฐานการเรียกเก็บเงินและบันทึกตรวจสอบ (audit) ไม่ถูกลบเพื่อแก้ข้อร้องเรียน**
   (ตรงกับ `docs/operations/SUPPORT_RUNBOOK.md` หัวข้อ Prohibited actions)
4. **ทุกครั้งที่ลบ ต้องมีบันทึกที่ตรวจสอบได้** — ใครสั่ง ใครทำ เมื่อไร ลบอะไร เพราะอะไร
   จำนวนเท่าไร และเหลืออะไรที่ไม่ลบพร้อมเหตุผล
5. **Dry-run ก่อนทุกครั้ง** — ดูรายการที่จะถูกลบก่อนลงมือจริง
6. **ผู้ทำและผู้ตรวจต้องไม่ใช่คนเดียวกัน** — คำขอที่อ่อนไหว (โดยเฉพาะคำขอของลูกค้า) ต้องมีคนที่สองยืนยัน
7. **ไม่มีอะไรผูกกับวันหมดอายุโดยอัตโนมัติ** — ขั้นตอนนี้เป็น manual ทั้งหมดจนกว่าจะมี job
   ที่ผ่านรีวิว (ดูข้อ 5)

(≈ `8760` ชั่วโมง) ตามข้อ 3 และต้องให้ Owner/ทนายยืนยันก่อนใช้กับข้อมูลจริง · ยังคง **ห้ามมี
default ในสคริปต์** — operator ต้องพิมพ์ค่าทุกครั้ง

**หมายเหตุถึง Owner:** ข้อ 3 เป็นช่องที่อันตรายที่สุด เพราะมีสองแรงดึงตรงข้าม —
เก็บนาน = ลูกค้าอ้าง PDPA, เก็บสั้น = ร้านเสียหลักฐานการชำระเมื่อมีข้อพิพาท
คำตัดสินนี้ต้องมาจากทนาย ไม่ใช่จากทีมเทคนิค (ร่าง A-27 ระบุไว้ตรงกัน)

**คำขอลบ "ตามคำขอ" (data-subject request) แยกจากตารางข้างบน:**

ให้เหลือ "บันทึกว่าลบแล้วเท่าไรและเก็บอะไรไว้เพราะอะไร" (ข้อ 2.4)

## 4. ขั้นตอนปฏิบัติ

### 4.1 เตรียมความพร้อมก่อนทำอะไรทั้งสิ้น

1. ยืนยันตัวตนผู้ขอ (สำหรับคำขอจากลูกค้า) และบันทึกช่องทาง/เวลาที่รับคำขอ
2. ยืนยันว่าคำขอนี้อยู่ในขอบเขตข้อ 1 และ **ไม่อยู่** ในข้อยกเว้นข้อ 2.2–2.3
3. ยืนยันว่ามี backup ล่าสุดที่กู้คืนได้จริง (อ้าง `docs/operations/BACKUP_RESTORE_RUNBOOK.md`)
4. เตรียมบันทึกการลบ (ข้อ 4.9) ตั้งแต่ก่อนเริ่ม — ถ้าลบแล้วค่อยจด จะได้ไม่ครบ

### 4.2 การลบตามอายุ (retention) — ทำเป็นรอบ ไม่ใช่ทำอัตโนมัติ

1. **ดูตัวอย่างก่อน (dry-run):** ใช้ `previewRetentionCleanup(shopId, cutoff)` ที่มีอยู่แล้วใน
   `apps/booking-admin/src/lib/ticket-service.ts` สำหรับตั๋วที่ปิดแล้ว เป็นแบบอย่างของรูปแบบ
   "ดูตัวอย่าง → ยืนยัน → ลบ" ที่ทีมนี้ใช้อยู่ (การลบต้องเป็นสองจังหวะเสมอ)
2. **สำหรับสลิปมัดจำ:** ใช้ `scripts/cleanup-stale-deposit-slips.mjs` ซึ่ง dry-run เป็นค่าเริ่มต้น
   และ **ไม่ลบสลิปที่ผูกกับ booking ทุกกรณี** ทั้งที่ยังใช้งานอยู่และที่ปิดแล้ว
   รวมถึงไม่ลบไฟล์ที่ยังมี grant อัปโหลดไม่หมดอายุ และไฟล์ที่อ่านอายุไม่ได้
   - ต้องระบุ `--min-age-hours` ทุกครั้ง (สคริปต์ไม่มีค่า default โดยเจตนา — ดูข้อ 3)
   - ตัวเลข `--min-age-hours` ต้องมาจากข้อ 3 ที่ Owner เติมแล้วเท่านั้น
3. **ยืนยันผลลัพธ์ด้วยคนที่สอง** ก่อนกดลบจริง (ข้อ 2.6)
4. **อย่าลบพร้อมกันหลายกลุ่มข้อมูล** ในรอบเดียว — แยกกลุ่ม เพื่อให้กู้คืนได้ถ้าพลาด

### 4.3 การลบตามคำขอของลูกค้า (data-subject request)

1. ทำข้อ 4.1 ให้ครบ
2. แยก Records ออกเป็นสามกอง **ก่อน** แตะข้อมูล:

   | กอง | ความหมาย | การกระทำ |
   | --- | --- | --- |
   | ลบได้ | ไม่ผูกกับหลักฐานที่ต้องเก็บ | ลบ |
   | ทำให้ไม่ระบุตัวตนได้ (anonymize) | ต้องเก็บโครงไว้เพื่อสถิติ/บัญชี แต่ไม่ต้องรู้ว่าเป็นใคร | แทนที่ข้อมูลระบุตัวตนด้วยค่าไม่ระบุตัว |
   | ต้องเก็บ | กฎหมาย/ข้อพิพาท/บัญชีบังคับ | เก็บ + บอกลูกค้าตามจริงว่าทำไม |

3. **หมายเหตุสำคัญ:** BK01 **ยังไม่มีฟังก์ชัน anonymize** ในระบบ — กอง "ทำให้ไม่ระบุตัวตนได้"
   ต้องรอ SQL scope ใหม่จากทีมที่ดูแลฐานข้อมูล (ดูข้อ 5) ห้ามใช้ `UPDATE` มือบนฐานที่ใช้งานร่วม
4. ลบไฟล์สลิปที่เกี่ยวข้องด้วย **เฉพาะ** เมื่อสลิปนั้นไม่ใช่หลักฐานที่ต้องเก็บ (อ้างข้อ 2.1)
   และเมื่อการลบไฟล์ไม่ทำให้แถวการจองอ้างไฟล์ที่หายไป — ถ้าลบไฟล์ ต้องจัดการ `slip_url`
   ให้สอดคล้องกัน ไม่งั้นข้อมูลจะเสียสภาพ
5. ส่งคำยืนยันให้ลูกค้าตามช่องทางที่อนุมัติ — **ช่องทางที่ A-27 ระบุสำหรับก่อนเปิดขายคืออีเมลของ
   Owner** (ยังต้องตั้งให้เป็นช่องทางทางการและทดสอบส่ง/รับจริง — ข้อ 5 B4) และข้อความนโยบาย
   ต้องไม่สัญญาระยะเวลาตอบกลับที่ยังทำไม่ได้ (`[[OWNER INPUT: response window]]`)

### 4.4 กฎเหล็ก: booking ที่มีเหตุการณ์เงิน (`deposit_money_events`) ห้าม DELETE — ใช้ anonymize เท่านั้น

**ข้อเท็จจริงที่ตรวจแล้ว:** `local_service.deposit_money_events` อ้าง `bookings` และ `shops`
**แบบไม่ cascade** และมี **trigger ห้ามแก้** (ผลตรวจโค้ดของผู้คุม, A-27 "ผลตรวจโค้ด")

ผลที่ตามมาและวิธีปฏิบัติ:

1. **ห้าม `DELETE` แถว `bookings` (หรือ `shops`) ที่มีเหตุการณ์เงินผูกอยู่ — ทุกกรณี** ไม่ว่าอายุจะครบ
   ไม่ว่าลูกค้าจะขอ ไม่ว่าจะสั่งด้วยมือหรือด้วยสคริปต์ · FK ที่ไม่ cascade จะทำให้คำสั่งล้มเหลว
   และถ้าไปดัดแปลงเพื่อให้ลบผ่านได้ จะทำให้หลักฐานการเงินเสียสภาพ
2. ทางที่ใช้ได้มีทางเดียวคือ **anonymize**: เขียนทับข้อมูลระบุตัวตน — **ชื่อ, เบอร์โทร, URL สลิป**
   เป็นค่าที่ไม่ระบุตัวตน แล้วเก็บโครง FK ไว้ครบ
3. **ห้ามแก้หรือปิด trigger เพื่อให้ลบผ่าน** — trigger คือด่านกันการทำลายหลักฐาน
4. **วันนี้ BK01 ยังไม่มีฟังก์ชัน anonymize** (ข้อ 5 B1) ⇒ งานรอบนี้ที่แตะ booking ที่มีเหตุการณ์เงิน
   **ทำได้แค่ระงับไว้ (Legal Hold Override ข้อ 4.5) แล้วส่งต่อ** ห้ามใช้ `UPDATE` มือบนฐานที่ใช้งานร่วม
5. ตัวเลขตามข้อ 3 (ข้อ 3) ยังบอกว่าเหตุการณ์เงิน **เก็บตลอดอายุบัญชีร้าน** และให้ร้านส่งออกก่อนปิดบัญชี
   — การส่งออกเป็นงานของร้าน ไม่ใช่เหตุให้เราลบ

### 4.5 Legal Hold Override — ขั้นตอนตรวจก่อนลบ *ทุกครั้ง*

**ต้องรันก่อนการลบทุกครั้ง ไม่มีข้อยกเว้น** แม้เป็นงานตามอายุ งานตามคำขอ หรือรอบรายไตรมาส:

1. **ตรวจก่อนว่ามี hold ไหม** — รายการที่ต้องตรวจ: ข้อพิพาท/ข้อร้องเรียนที่ยังไม่ยุติ, คิวที่อยู่
   ระหว่างการคืนมัดจำ, เรื่องที่อยู่ระหว่างการสอบสวนด้านความปลอดภัย, คำขอจากหน่วยงานรัฐ/กระบวนการ
   ทางกฎหมาย, และรายการที่ฝ่ายบัญชียังไม่ปิดรอบ
2. **ถ้ามี hold หรือไม่แน่ใจ → "เก็บ" และหยุดรายการนั้น** หลักการเดียวกับทั้งคู่มือนี้:
   เกณฑ์ที่ผิดต้องนำไปสู่ "เก็บ" ไม่ใช่ "ลบ"
3. **ระงับเฉพาะข้อมูลที่เกี่ยวข้องกับ hold นั้น** ไม่ระงับทั้งชุด — ข้อมูลอื่นที่พ้น hold แล้ว
   กลับเข้ากระบวนการปกติได้
4. **จดลงบันทึกการลบ (ข้อ 4.9) ทุกครั้ง** ทั้งกรณี "ระงับเพราะ hold" และกรณี "กลับเข้าสู่กระบวนการ"
   ว่าใครเป็นผู้ปลด hold เมื่อไร
5. **วันนี้ยังไม่มีระบบ hold แบบอัตโนมัติ** — ขั้นตอนนี้เป็น manual และต้องอาศัย operator
   ยืนยันกับ Owner/ฝ่ายบัญชี/ฝ่ายสนับสนุน (ข้อ 5 B6) · ห้ามสมมติว่า "ไม่มี hold"

### 4.6 ต้องทำหลัง restore ฐานข้อมูล — replay deletion log/tombstone ก่อนเปิดระบบ

**บริบท:** ข้อมูลสำรองเก็บ 60 วันหลังปิดบัญชี (ข้อ 3 ข้อ 8) และ **การลบไม่ได้ลบย้อนหลังไปใน
backup** ถ้า restore กลับมาแล้วเปิดระบบทันที ข้อมูลที่ลบไปแล้วจะ **กลับมามีชีวิต** ซึ่งผิดทั้งต่อ
คำขอของลูกค้าและต่อนโยบายของเรา

**ขั้นตอนบังคับ (ทำทุกครั้งหลัง restore ก่อนเปิดระบบให้ผู้ใช้เข้าถึง):**

1. **หยุดการเปิดให้บริการ** — ระบบต้องอยู่ในสถานะที่ผู้ใช้ยังเข้าถึงข้อมูลไม่ได้ระหว่างขั้นตอนนี้
2. **นำ deletion tombstone / deletion log ที่บันทึกไว้ตั้งแต่หลังวันที่ของ backup มาทับ (replay)**
   รายการที่ถูกลบไปแล้ว ⇒ ต้องไม่มีข้อมูลที่ลบแล้วกลับมาให้ผู้ใช้เห็นไม่ว่ากรณีใด
3. **ต้องมีที่เก็บ tombstone แยกจากฐานข้อมูลที่ restore มา** (tombstone ต้องไม่ถูก restore ทับ)
   — ถ้ายังไม่มีที่เก็บนี้ **ห้ามเปิดระบบ** และต้องรายงานเป็น blocker
4. **ยืนยันผลด้วยคนที่สอง** แล้วจดในบันทึกการลบ (ข้อ 4.9) ว่า replay อะไรไป จำนวนเท่าไร
   และตรวจอะไรแล้วบ้าง
5. **ห้ามใช้ "ข้อมูลที่ restore มาแล้วดูครบ" เป็นเหตุผลให้ข้ามข้อนี้** — ความครบคืออาการของปัญหา

> **หมายเหตุตรงไปตรงมา:** กลไก deletion tombstone **ยังไม่มีในระบบวันนี้** (ข้อ 5 B7)
> ข้อ 4.6 จึงยังบังคับใช้ไม่ได้จริงจนกว่าจะมีที่เก็บและรูปแบบ tombstone — เขียนไว้เพื่อ **ห้าม
> ประกาศว่าระบบรองรับแล้ว** และเพื่อให้ข้อกำหนดนี้ถูกส่งเป็นสัญญาไปกับ R1–R4

### 4.7 ลบตามรอบทุกไตรมาสสำหรับร้านที่เลิกใช้ระบบเกิน 12 เดือน (ขั้นตอนมือ)

**ที่มา:** A-27 "ก่อนขาย" — ลบตามรอบทุกไตรมาสสำหรับร้านที่ปิด ⇒ งานนี้เป็น **manual ไม่ใช่อัตโนมัติ**
และรันเป็นรอบ ไม่ใช่ต่อเนื่อง

รอบการทำงาน (ต่อหนึ่งรอบ):

1. **ตั้งรอบตายตัว** — หนึ่งครั้งต่อไตรมาส และ **บันทึกวันที่จะรันรอบถัดไปไว้ล่วงหน้า**
2. **คัดร้านเข้าเกณฑ์** — ร้านที่เลิกใช้/ปิดบัญชีแล้ว และ **พ้น 12 เดือน** นับจากวันที่เลิกใช้ (ข้อ 3 ข้อ 1)
   อย่านับจากวันปิดตั๋วหรือวันอื่น
3. **ตรวจ Legal Hold Override ทุกครั้ง** (ข้อ 4.5) — ร้านที่มีข้อพิพาท/ค้างคืนมัดจำ/สอบสวน ให้ตัดออก
   จากรอบนี้โดยไม่ต้องถามซ้ำ
4. **Dry-run ก่อนเสมอ — ห้ามข้าม:**
   - ใช้สคริปต์ที่มีอยู่จริงเท่านั้น: `scripts/cleanup-stale-deposit-slips.mjs`
     (dry-run เป็นค่าเริ่มต้น · **ไม่ลบสลิปที่ผูกกับ booking ทุกกรณี** · ต้องระบุ `--min-age-hours` ทุกครั้ง)
   - ดูรายการ `deletable` / `kept` และเหตุผลของแต่ละรายการก่อนอนุมัติ
5. **ยืนยันด้วยคนที่สอง แล้วจึงรันแบบลบจริง** (ยังต้องมี `--confirm-plan <sha256>` จาก dry-run
   ที่รีวิวแล้ว — ไม่มีทางลัด)
6. **สำหรับ booking ที่มีเหตุการณ์เงิน: ห้าม DELETE — ทำตามข้อ 4.4** (ระงับ + ส่งต่อ)
7. **จดบันทึกการลบ (ข้อ 4.9) ทุกครั้ง** ระบุจำนวนที่ลบ จำนวนที่เก็บและเหตุผล (ห้ามเว้น)
8. **อย่ารวมรอบนี้กับงานตามคำขอของลูกค้า** ในครั้งเดียวกัน (ข้อ 4.2)

### 4.8 สิ่งที่ผิดเสมอ (ห้ามทำ)

- **`DELETE` แถว `bookings` ที่มี `deposit_money_events` ผูกอยู่ — ทุกกรณี** (FK ไม่ cascade + trigger
  ห้ามแก้) · ทางเดียวที่ใช้ได้คือ anonymize (ข้อ 4.4)
- **แก้หรือปิด trigger / FK เพื่อให้การลบผ่าน** — เท่ากับทำลายหลักฐานการเงิน
- **เปิดระบบหลัง restore โดยไม่ replay deletion log/tombstone** (ข้อ 4.6)
- **ลบโดยไม่ตรวจ Legal Hold Override ก่อน** (ข้อ 4.5)
- ลบสลิปของ booking ที่ยังไม่พ้นช่วงโต้แย้ง แม้ลูกค้าจะขอ
- ลบแล้วไม่จดบันทึก
- ลบด้วยคำสั่งมือบนฐาน production โดยไม่มี dry-run และไม่มีคนที่สอง
- ใช้ service-role key ในเครื่องมือที่ไม่ผ่านรีวิว (นโยบาย BK01: product code ไม่ถือ service-role)
- ลบข้อมูลสำรอง (backup) ด้วยมือเพื่อให้ "ดูเหมือนลบแล้ว" — backup มีรอบของตัวเอง

## 8. บันทึกความไม่แน่ใจ

- **ตัวเลขในข้อ 3 มาจาก A-27 (Owner ตอบ "ตามนี้" 2026-10-02) — ไม่ใช่จากผู้เขียนเอกสารนี้**
  ผู้เขียนคัดตัวเลขมาตรง ๆ และไม่ตัดสินใจแทน Owner/ทนาย ทุกช่องที่ต้องยืนยันทางกฎหมายกำกับไว้แล้ว
- ตัวเลข "60 วัน" (backup) ตรงกับข้อความกฎหมายปัจจุบันและ A-27 — ยังคงเป็นคำตัดสินของ Owner
- ผู้เขียนไม่ได้อ่านนโยบาย PDPA ฉบับเต็มหรือคำแนะนำทางกฎหมายฉบับใด การอ้าง "กฎหมายบังคับ"
  ในคู่มือนี้เป็น **ช่องว่างที่ต้องให้ทนายเติม** ไม่ใช่ข้อสรุปทางกฎหมาย
- **ผู้เขียนตรวจโครงสร้าง FK/trigger ของ `deposit_money_events` จากรายงานผลตรวจโค้ดของผู้คุม
  ใน A-27 ไม่ได้อ่าน DDL เอง** (ไฟล์ P0 `…120000` ไม่อยู่ใน worktree นี้) — ก่อนใช้คำสั่งจริง
  ต้องยืนยันกับ DDL จริงอีกครั้ง
- ขอบเขตข้อ 1 มาจากการค้นโค้ด (`supabase/` + `apps/`) ตาม G33 ไม่ได้มาจากการสำรวจฐานข้อมูลจริง
- **กลไกทั้งหมดที่อ้างในข้อ 4.6 และ 4.7 (tombstone, รอบไตรมาส, hold flag) ยังไม่มีในระบบวันนี้**
  เอกสารนี้เขียนเป็นข้อกำหนด/ขั้นตอนมือ ไม่ใช่คำอธิบายของระบบที่ทำงานแล้ว
