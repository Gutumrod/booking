# OWNER BRIEF — BK01 ทดสอบร้านจริงและยกระดับก่อนขายวงกว้าง

**วันที่:** 9 กันยายน 2026
**เอกสารคู่กัน:** `BRIEF-BK01-REAL-SHOP-PILOT-HARDENING-2026-09-09.md`
**ความหมาย:** ต้องตรงกับ Execution Brief ทุกข้อ ต่างกันเฉพาะภาษาที่อ่านง่ายกว่า

## เรากำลังทำอะไร

แนวคิดที่ล็อกคือ **รีบ deploy แบบควบคุม เพื่อให้ร้านจริงลองใช้และหา defect ให้เจอก่อนขายวงกว้าง**
KMO เป็นสนามทดลองแรก แต่ BK01 ห้ามถูกออกแบบให้เหมาะกับ KMO ร้านเดียว
เราจะใช้สิ่งที่ KMO เจอเป็นหลักฐาน แล้วถามต่อทุกครั้งว่า “ร้านแบบอื่นจะเจอด้วยไหม?”

เป้าหมายคือ BK01 ต้องรองรับร้านหลายสไตล์ ทั้ง Booking และไม่ปิดทาง Order / Claim ในอนาคต

## กฎใหญ่ที่สุด

**สิ่งที่ร้านแต่ละร้านอาจทำไม่เหมือนกัน ต้องตั้งค่าได้**
**สิ่งที่เกี่ยวกับความปลอดภัยและความถูกต้องของระบบ ต้องล็อกตายและข้ามไม่ได้**

ตัวอย่างสิ่งที่ร้านควรตั้งเองได้: วันหยุด เวลาเปิดร้าน ตารางพนักงาน ระยะเวลาบริการ มัดจำ การยกเลิก/เลื่อน และรูปแบบการรับจอง
ตัวอย่างสิ่งที่ร้านห้ามแก้ข้าม: tenant isolation, สิทธิ์ผู้ใช้, ป้องกันคิวชน, transaction, idempotency, payment integrity และ audit trail.
## สิ่งที่ KMO ทดลองแล้วเจอ

1. ตั้งวันเปิด/ปิดร้านได้และบันทึกได้ — ใช้งานได้จริง
2. ช่องเวลาใช้งานยากบนอุปกรณ์ที่ลอง — ต้องแก้ UX
3. หน้าลูกค้า/การ preview ไม่ชัด และถ้ายังไม่มีบริการระบบอธิบายไม่ดี — ต้องแก้ onboarding/readiness
4. วันหยุดพิเศษเพิ่ม/ลบได้ — ใช้งานได้จริง
5. เวลาร้านกับตารางพนักงานแยกกัน และแก้หลายคนแล้ว save คนหนึ่งทำค่าคนอื่นที่ยังไม่ save หาย — P0
6. โปรไฟล์ร้าน save ไม่ได้ถ้ายังไม่มี PromptPay — P0 และเป็นปัญหา generic ของ BK01
7. ระยะเวลาบริการมีแต่ “นาที” และมีสมมติฐาน 15 นาที — ไม่พอสำหรับร้านหลายประเภท
8. ช่องตัวเลขลบจนว่างไม่ได้ เพราะระบบแปลงช่องว่างเป็น 0 ทันที — UX defect
9. หน้าลูกค้า HTTP 200 ได้แต่ยังไม่มี booking flow ที่ใช้จริง — P0; HTTP 200 ไม่ถือว่าผ่าน

## เรื่องวันหยุดที่ต้องเปลี่ยน contract

ร้านต้องเลือกโหมดวันหยุดประจำสัปดาห์แบบใดแบบหนึ่ง:

### A — ร้านกำหนดวันหยุดประจำสัปดาห์
ร้านกำหนดวันเปิด/ปิดประจำสัปดาห์ และปิด control วันหยุดประจำสัปดาห์รายพนักงาน

### B — พนักงานกำหนดวันหยุดประจำสัปดาห์แยกกัน
พนักงานแต่ละคนมีวันทำงาน/วันหยุดเอง และปิด control วันหยุดประจำสัปดาห์ระดับร้าน

ไม่ว่าจะเลือก A หรือ B:
- วันหยุดพิเศษของร้านแบบระบุวันที่ยังใช้ได้เสมอ
- วันลา/หยุดเฉพาะวันที่ของพนักงานยังใช้ได้เสมอ
## เวลา บริการ และการตั้งค่าที่ต้องยืดหยุ่น

ระบบห้ามฝัง slot 30 นาที หรือ duration 15 นาทีเป็นกฎของร้านทุกประเภท
ร้านควรกำหนด slot interval และรูปแบบระยะเวลาบริการได้ตาม contract

บริการแบบนาที/ชั่วโมงสามารถอยู่ในโมเดลคิวเวลาเดียวกันได้ แต่บริการแบบ “หลายวัน” ต้องเป็นอีก scheduling mode ที่เข้าใจการข้ามวันจริง ไม่ใช่เอาจำนวนวันคูณ 1,440 นาทีแล้วจบ

หน้า Admin ต้องแก้เรื่อง:
- ช่องเวลา: พิมพ์ HH:MM ได้ง่าย และมี picker ที่ใช้งานง่าย
- ช่องตัวเลข: ลบจนว่างได้ระหว่างพิมพ์ แล้วค่อย validate ตอน save
- ตารางหลายพนักงาน: ค่าที่แก้ค้างไว้ห้ามหายเพราะ save อีกคน
- ควรมี Save All Changes หรือระบบเตือน unsaved changes ชัดเจน
- ต้องมีปุ่ม Preview customer page ให้ดูได้ตลอด แม้ร้านยังตั้งค่าไม่ครบ

## Profile ต้องไม่ผูก Payment

ร้านต้องแก้ชื่อ เบอร์โทร ที่อยู่ และข้อมูลทั่วไปได้โดยไม่ต้องใส่ PromptPay
Payment เป็นการตั้งค่าอีกส่วนหนึ่ง
ถ้าร้านเปิดมัดจำแต่ยังไม่มี payment method ที่ตรวจสอบแล้ว ระบบต้องปิด flow การจ่ายเงินอย่างปลอดภัยและบอกเหตุผลชัดเจน
ห้ามสร้างเลข PromptPay ปลอม ห้ามเดายอดมัดจำ และห้ามเปลี่ยนมัดจำเป็น 30% อัตโนมัติเพียงเพราะราคาเปลี่ยน
## หน้าร้านต้องบอกความพร้อมแบบตรงไปตรงมา

Admin ควรบอกเป็นหัวข้อว่าอะไรพร้อมแล้ว อะไรยังขาด เช่น โปรไฟล์ ตารางร้าน บริการ พนักงาน Payment เมื่อจำเป็น และสถานะรับจองออนไลน์
ร้านต้องเปิดดูหน้าลูกค้าได้ก่อนตั้งค่าครบทั้งหมด

หน้าลูกค้าห้ามว่างเฉย ๆ ต้องบอกได้ว่า:
- ร้านยังไม่พร้อม/ถูกปิดรับจอง
- ยังไม่มีบริการ
- ยังไม่มีพนักงานหรือ provider ที่ต้องใช้
- ตารางยังไม่พร้อม
- วันที่เลือกไม่มีคิว
- ต้องตั้ง Payment ก่อนเพราะ flow นี้ใช้มัดจำ
- หรือเกิด runtime/data error จริง

## เราจะไม่เทสแค่ KMO

ต้องเอา contract ไปทดสอบกับร้านหลายแบบอย่างน้อย:
- ร้านตัดผม/เสริมสวย: คิวสั้น หลายพนักงาน
- คลินิก/เวลเนส: provider ชัด มีช่วงพักและ policy ยกเลิก
- อู่/ร้านซ่อม: งานเวลายาวไม่เท่ากัน
- ร้านรับทำของแบบ KMO: งานยาว มี production และอนาคตมี Order/Claim
- ร้านไม่เก็บมัดจำ
- ร้านคนเดียว
- ร้านหลายพนักงานที่แก้ตารางพร้อมกัน
- งานหลายวัน/date range
- ร้านที่เน้น Claim/Support มากกว่า Booking

เป้าหมายคือแก้ให้เป็น generic merchant capability ไม่ใช่แก้ KMO แล้วฝัง KMO เข้า product.
## ความปลอดภัยที่ต้องเพิ่มความเข้มงวด

ทุกฟีเจอร์ใหม่ต้องพิสูจน์จาก DB/RPC จริงว่า:
- owner/admin เท่านั้นที่แก้สิ่งที่ควรแก้ได้
- staff ธรรมดาถูกปฏิเสธเมื่อ contract ไม่อนุญาต
- outsider และร้านอื่นอ่าน/แก้ข้าม tenant ไม่ได้
- public เห็นเฉพาะข้อมูลขั้นต่ำที่ต้องใช้จอง
- browser ไม่มี service-role หรือ secret หลุด
- การสร้าง/เลื่อนคิวกันคิวชนจริงแม้ยิงตรง RPC
- operation ที่ retry ได้ต้องมี idempotency
- การเปลี่ยนค่าที่สำคัญมี audit evidence
- pilot schema patch ต้อง rollback ได้
- payment instruction จะออกได้ต่อเมื่อ recipient/config ถูกยืนยันแล้ว

Booking, Order และ Claim ไม่จำเป็นต้องใช้ calendar ตารางเดียวกัน เพราะความหมายงานต่างกัน
ห้ามยุบทุกอย่างเป็นก้อนเดียวเพียงเพราะทำง่าย และห้ามสร้าง generic ERP ใหญ่เกินจำเป็น

## แผนจากตรงนี้

1. ล็อกหลักฐาน KMO ทั้ง 9 ข้อ
2. Audit hardcode ทั้ง Admin / Consumer / SQL-RPC / Booking / Ticket-Claim / Order preparation
3. ล็อก Scheduling Contract V2
4. แยก Profile / Schedule / Service / Payment / Readiness ให้ชัด
5. ออกแบบ UX remediation และ service scheduling ใหม่
6. Security review + negative tests แบบเข้ม
7. รอ House คืน `Junction A PASS` และให้ BK01 re-prove ก่อนทำ canonical LAB migration
8. หลังผ่านจึง implement bounded change, ทดสอบ LAB isolation, sync กลับ KMO และ deploy pilot รอบสอง

ระหว่างนี้ KMO downstream ใช้เป็นสนามทดลองแบบควบคุมได้ แต่ยังไม่ถือว่า customer-ready จน P0 customer flow ผ่าน
## จะถือว่าผ่านเมื่อไหร่

โค้ดเขียวอย่างเดียวไม่พอ ต้องผ่านทั้ง test/build, DB/RPC, permission/tenant negative tests, browser/mobile usability และ customer E2E จริง
ต้องพิสูจน์ทั้งเส้นทางที่จองได้และเส้นทางที่ควรถูกปฏิเสธ
ต้อง reload แล้วค่าร้านไม่หาย และไม่มี fallback ปลอมสร้าง business truth ขึ้นมาเอง

## ต้องหยุดทันทีเมื่อ

- ต้องเดาข้อมูลร้านหรือข้อมูลรับเงิน
- ต้องลดความปลอดภัยเพื่อให้ flow ผ่าน
- ต้อง migrate WSTERA LAB ก่อน Junction A ผ่าน
- ต้องเอาค่าเฉพาะ KMO ไป hardcode ใน BK01
- ต้องเปิด Order/Claim live เพื่อแก้ปัญหา Booking
- มี delta ไปโดน PS01 / MT01 / shared runtime โดยไม่ตั้งใจ
- มีหลักฐานแค่ HTTP 200, mock หรือ source inspection แต่ยังไม่มี real-user proof ตาม gate

**คำตัดสินตอนนี้:** BK01 ต้องผ่าน Real-Shop Hardening ก่อนขายวงกว้าง
แต่การ deploy แบบควบคุมยังควรทำต่อ เพราะมันคือเครื่องมือสำคัญในการหา defect จากการใช้งานจริง
## เงื่อนไข Pilot ที่ต้องจำเหมือน Execution Brief

การ deploy เร็วเป็นสนามเรียนรู้ ไม่ใช่หลักฐานว่า release-ready
ใช้ข้อมูลร้านจริงและบัญชี owner/staff จริงได้ แต่ก่อน P0 customer flow ผ่าน ให้ใช้ข้อมูลลูกค้าทดสอบที่ไม่อ่อนไหวและ transaction ทดสอบเท่านั้น
ห้าม customer cutover โดยไม่ได้อนุมัติ และห้ามใช้ recipient/payment identity ที่เดาหรือปลอมขึ้นมา

ลำดับตัดสินว่าคิวจองได้ต้องตรงกันทุกช่องทาง:
`ร้าน/สิทธิ์รับจอง -> วันหยุดพิเศษร้าน -> weekly mode ที่ร้านเลือก -> วันลาพนักงานเฉพาะวันที่ -> เวลาทำงาน/พัก -> คิวชน -> จองได้`
Consumer, create hold, reschedule และ trusted mutation ต้องใช้กฎเดียวกัน; ซ่อนปุ่มใน UI อย่างเดียวไม่ถือว่าปลอดภัย

การตรวจเบอร์ลูกค้าต้องมี policy เดียวกันระหว่าง Booking และ Ticket/Claim
ถ้าจะเป็น Thailand-first ต้องประกาศให้ชัดว่าเป็น product policy และ normalize อย่างเดียวกัน ห้ามมี regex คนละชุดฝังตามหน้าต่าง ๆ

ก่อนเรียก feature ว่า PASS ต้องมีครบตามที่เกี่ยวข้อง: static/type/lint/build, domain/DB-RPC, negative permission/tenant, browser/mobile usability, customer E2E ทั้งบวกและลบ, reload แล้วค่าไม่หาย, ไม่มี fallback ปลอม และมี rollback/recovery evidence สำหรับ pilot runtime change

Canonical BK01 ยังอยู่ใต้ Junction A gate: ตอนนี้ทำ audit/design/test/docs ได้ แต่ห้าม forward migration ใน WSTERA LAB และห้ามเริ่ม Order/Claim live integration จน House คืน PASS และ BK01 re-prove สำเร็จ
