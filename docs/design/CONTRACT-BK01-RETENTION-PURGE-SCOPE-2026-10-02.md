## 2. ข้อเสนอเป็นคำขอ (4 ข้อ — Owner/House เลือกได้ว่าจะเอาข้อไหน)

### กฎร่วมที่ใช้กับ **ทุก** ข้อ (บังคับจาก A-27 — ห้ามเลือกทำบางข้อ)

**D1 — แยกสองทาง: anonymize สำหรับ booking ที่มีเหตุการณ์เงิน · DELETE เฉพาะแถวที่ไม่มี FK ผูก**

- แถว `local_service.bookings` (หรือ `shops`) ที่มีเหตุการณ์เงินใน `local_service.deposit_money_events`
  **ห้าม DELETE ทุกกรณี** — FK ของ `deposit_money_events` **ไม่ cascade** และมี **trigger ห้ามแก้**
  (ผลตรวจโค้ดของผู้คุม, A-27) ⇒ ระบบลบอัตโนมัติต้อง **anonymize** แถวนั้นแทนการลบ
  โดยเขียนทับข้อมูลระบุตัวตนเท่านั้น: **ชื่อ, เบอร์โทร, URL สลิป**
- **DELETE ใช้ได้เฉพาะแถวที่ไม่มี FK ใดผูกอยู่จริง** — ถ้ามี FK อ้างถึงแถวนั้น (ไม่ว่า cascade หรือไม่)
  ต้อง **anonymize** ไม่ใช่ลบ
- **ห้ามแก้ FK หรือปิด trigger เพื่อให้ DELETE ผ่าน** — นี่คือข้อห้ามที่หนักที่สุดในสัญญานี้
- ผลตรวจโค้ดเดิมใน §4 (planner fail-closed) ยังบังคับใช้: อ่านข้อมูลไม่ได้ = ไม่ลบ ไม่ anonymize
  — ให้ **หยุดและรายงาน**

**D2 — retention ที่ผิดต้องไปทาง "เก็บ"** (ทับซ้อนกับ §4) และทุกการลบ/anonymize ต้องมี audit row

**D3 — Legal Hold ต้องเป็นด่านหน้า:** ก่อนลบ/anonymize ทุกครั้ง ต้องมีจุดตรวจว่าแถวนั้นถูก hold
หรือไม่ (สัญญาขอให้ออกแบบที่เก็บ flag; ตัวระบบ hold ไม่มีวันนี้ — ดู R4/§6)

**พารามิเตอร์ตัวเลข:** ค่าจาก A-27 = customers/bookings 12 เดือนหลังร้านเลิกใช้ · cancelled 12 เดือน
หลังวันนัด · สลิป 12 เดือน · LINE log 90 วัน · tickets 12 เดือน · audit 12 เดือน · billing ≥ 5 ปี ·
backup 60 วัน · `deposit_money_events` เก็บตลอดอายุบัญชี · **ห้าม hard-code** — ต้องรับเป็นค่าตั้งต้น
ที่ปรับได้ เพราะข้อ 3/6/7 ยังรอทนาย/บัญชียืนยัน

### R1 — เก็บกวาด grant ที่หมดอายุ (ราคาถูกสุด, ความเสี่ยงต่ำ)

**ต้องการ:** กลไกที่ลบแถว `local_service.deposit_slip_upload_grants` ที่ `expires_at < now() - grace`
**ทำไม:** แถวที่หมดอายุแล้วไม่ถูกใช้ตัดสินใจอะไรอีก (การ consume เป็น one-shot ที่ House trigger)
การค้างไว้ทำให้ตารางโตแบบไม่มีเพดานตามจำนวนการยิงที่ G36 ตรวจพบ
**ข้อห้ามที่ต้องคงไว้:**
- ห้ามลบแถวที่ `expires_at > now()` — นั่นคือ upload ที่ลูกค้ายังทำค้างอยู่
- ห้ามลบแถวที่ `object_path` ตรงกับ `bookings.slip_url` ใด ๆ (หลักฐาน) แม้จะหมดอายุแล้ว
- ต้องเพิ่ม index ให้ query นี้ไม่กลายเป็น sequential scan บนตารางที่โต
**คำถามที่ต้องให้ Codex ตัดสิน (พร้อมเหตุผล):** ควรเป็น SECURITY DEFINER RPC ที่เรียกจาก job/
scheduler หรือเป็น House-owned job? ใครถือ EXECUTE? ถ้าเพิ่ม RPC ต้องเพิ่มใน allowlist — คุ้มไหม
เทียบกับให้ House เก็บกวาดเอง

### R2 — เก็บกวาดวัตถุใน storage ที่ไม่มีใครอ้าง (ราคากลาง, ต้องตัดสินให้ชัด)

**ต้องการ:** รายการ (ไม่ใช่การลบอัตโนมัติ) ของวัตถุใน `deposit-slips` ที่
(ก) ตรงรูปแบบ path `<booking_uuid>/<grant_uuid>.<ext>`
(ข) `created_at` เก่ากว่าเกณฑ์
(ค) ไม่ตรงกับ `bookings.slip_url` ใด ๆ
(ง) ไม่มี grant ที่ยังไม่หมดอายุชี้มาที่ path นั้น
**ทำไม:** สคริปต์ฝั่งแอป (`scripts/cleanup-stale-deposit-slips.mjs`) ทำได้แล้ววันนี้ในโหมด
dry-run ผ่าน Storage HTTP API แต่ต้องพึ่ง operator ดึงข้อเท็จจริงเองและถือ service key —
การมี read surface ที่ปลอดภัยกว่านี้จะลดความเสี่ยง operator
**ข้อห้ามที่ต้องคงไว้:**
- **ห้ามลบวัตถุที่ `bookings.slip_url` อ้างถึงทุกกรณี** ไม่ว่าการจองจะเก่าหรือปิดแล้ว
- ห้ามลบวัตถุที่อ่าน `created_at` ไม่ได้
- ห้ามลบวัตถุที่ยังมี grant ไม่หมดอายุ
**คำถามที่ต้องให้ Codex ตัดสิน:** ควรมี read-only RPC/view ที่คืน *รายการ* ให้ operator ตรวจ
(และ operator เป็นคนลบผ่าน Storage API ที่มีอยู่) แทนที่จะให้ SQL สั่งลบเองหรือไม่ — ผู้เขียน
เอนไปทาง read-only เพราะลดความเสียหายถ้าเกณฑ์ผิด แต่เป็นคำตัดสินของ Codex/House

### R3 — anonymize + DELETE แบบแยกทาง (ราคาแพงสุด, ต้องมีก่อนประกาศว่ามีระบบอัตโนมัติ)

**ต้องการ:** ความสามารถทำให้ข้อมูลระบุตัวตนของลูกค้าไม่ระบุตัวได้ **โดยไม่ทำลายความสมบูรณ์ของ
foreign key** และไม่ลบหลักฐานที่กฎหมายบังคับให้เก็บ — พร้อมกลไกลบได้จริงสำหรับแถวที่ไม่มีอะไรผูก

**ทางที่ต้องมีสองทางแยกกันชัดเจน (กฎ D1):**

| กรณีของแถว | การกระทำที่อนุญาต | เหตุผล |
| --- | --- | --- |
| ไม่มี FK ใดอ้างถึง | **DELETE ได้** เมื่อครบอายุ | ไม่มีอะไรเสียหาย |
| มี FK อ้างถึง (เช่น `bookings` ที่มี `deposit_money_events`) | **ห้าม DELETE — anonymize เท่านั้น** (ชื่อ, เบอร์โทร, URL สลิป เป็นค่าไม่ระบุตัว) | FK ไม่ cascade + trigger ห้ามแก้ ⇒ ลบไม่ได้ และการดัดแปลงให้ลบได้ = ทำลายหลักฐานการเงิน |
| อยู่ระหว่างข้อพิพาท/สอบสวน/บัญชียังไม่ปิด | **ระงับ (hold)** | กฎ Legal Hold Override |

**ทำไม:** `request_account_closure` (migration :604) เป็นเพียงการ INSERT คำขอ —
ไม่มีกลไกทำตามคำขอ (G33, LANE F-14) และ A-27 ระบุว่า **หลังเปิดขาย** ระบบลบอัตโนมัติต้องเป็น
anonymize ไม่ใช่ DELETE กับ booking ที่มีเหตุการณ์เงิน

**ข้อห้ามที่ต้องคงไว้:**
- ห้าม DELETE แถว `bookings`/`shops` ที่มีเหตุการณ์เงิน (`deposit_money_events`) **ทุกกรณี**
- **ห้ามแก้ FK / ปิด trigger** เพื่อให้ DELETE ผ่าน
- ห้าม DELETE แถวที่มี FK ใดอ้างถึง (generalize จากข้อบน — อย่าไล่แก้ทีละตาราง)
- ต้องไม่ทำให้ `bookings.slip_url` ชี้ไฟล์ที่หายไป (สอดคล้องกับ R2)
- ต้องมีบันทึก audit ของการ anonymize **และการลบ** ทุกครั้ง (ใคร เมื่อไร แถวใด ค่าเก่าถูกแทนด้วยอะไร)
- anonymize ต้อง **ไม่** แตะยอดเงิน วันที่ และรหัสอ้างอิงของการเงิน — เปลี่ยนเฉพาะข้อมูลระบุตัวตน
- ต้อง **ไม่** แตะแถวที่ถูก hold
**คำถามที่ต้องให้ Codex ตัดสิน:** field ใดนับเป็น "ข้อมูลระบุตัวตน" ในสคีมาปัจจุบัน (`customers`,
`line_users`, `bookings.notes`?) — ผู้เขียนไม่ตัดสินแทน เพราะกระทบสัญญาและ PDPA

### R4 — deletion tombstone (จำเป็นต่อข้อกำหนด restore→replay — ราคา: ต้องออกแบบ)

**ต้องการ:** ที่เก็บ **deletion/anonymize tombstone แยกจากฐานข้อมูลที่ backup ไว้** และ replay ได้
— ระบุอย่างน้อย: ชนิดการกระทำ (delete/anonymize), ตาราง, คีย์ของแถว, เวลาที่ทำ (UTC),
ผู้สั่ง/ผู้ทำ, hash ของแผนที่อนุมัติ

**ทำไม:** ข้อมูลสำรองเก็บ 60 วันหลังปิดบัญชี (A-27 ข้อ 8) และ **backup ไม่รู้จักการลบที่เกิดทีหลัง**
ถ้า restore แล้วเปิดระบบ ข้อมูลที่ลบไปแล้วจะกลับมามีชีวิต ⇒ A-27 บังคับว่า
**"หลัง restore ต้อง replay deletion tombstone ห้ามข้อมูลที่ลบแล้วกลับมา"**
(ขั้นตอนปฏิบัติอยู่ที่ runbook §4.6)

**ข้อห้าม/ข้อบังคับ:**
- tombstone **ต้องไม่** ถูก restore ทับ (ที่เก็บต้องอยู่นอกชุดที่ restore)
- restore ที่ replay ไม่ครบ ⇒ **ห้ามเปิดระบบ** (fail-closed) และต้องรายงานเป็น blocker
- ตัว tombstone เองเป็นบันทึกการลบ จึงต้องตรวจสอบย้อนหลังได้และห้ามลบ
- **วันนี้ยังไม่มีกลไกนี้** ⇒ ก่อนมี ระบบต้องถือว่า "restore แล้วต้องหยุด" ไม่ใช่ "restore แล้วใช้ได้"

**คำถามที่ต้องให้ Codex/House ตัดสิน (พร้อมเหตุผล):** ควรเก็บ tombstone ที่ไหน (ตาราง House /
storage / log append-only) และใครเป็นเจ้าของการ replay — BK01 หรือ House?

## 3. สิ่งที่ผู้เขียน "ไม่" ขอ (เพื่อไม่ให้ขอบเขตบาน)

- ไม่ขอให้แก้ RLS/policy ที่มีอยู่
- ไม่ขอให้เปลี่ยนโครง `deposit_slip_upload_grants` หรือ return shape ของ
  `authorize_deposit_slip_upload`

- ไม่ขอให้แตะ House SQL (`wstera_platform_internal.*`) เว้นแต่ House อนุมัติเอง
- ไม่ขอให้ทำ R1–R4 **ก่อนเปิดขาย** — A-27 กำหนดว่าเป็นงานหลังเปิดขาย; ก่อนเปิดขายใช้
  runbook ลบด้วยมือ + สคริปต์ dry-run ที่มีอยู่ (แต่ R4 ต้องมี**ก่อน**จะเชื่อว่า restore ปลอดภัย)

**หลักการที่ต้องคงไว้ในทุกข้อ:** เกณฑ์ที่ผิดต้องนำไปสู่ "เก็บ" ไม่ใช่ "ลบ"
(ทุกกรณีที่อ่านข้อมูลไม่ได้ → ไม่ลบ) และทุกการลบต้องมีบันทึกที่ตรวจสอบย้อนหลังได้

## 5. แก้ไขเพิ่มหลังรีวิวรอบ R2 (2026-10-02)

ผู้ตรวจอิสระสองคน (opencode + AGY) รีวิว `4d067fd` แล้วพบ 4 ข้อที่ **แก้แล้วในงานรอบ R2**
บันทึกไว้ที่นี่เพื่อให้ Codex เห็น "สัญญาณที่ห้ามทำซ้ำ" เมื่อต่อยอด ไม่ใช่แค่รายการฟีเจอร์:

- **F1 (HIGH) — uuid ต้องเป็น canonical ก่อนเป็นคีย์:** เดิมคีย์งบต่อ booking ใช้สตริงดิบ
  แต่ RPC รับ `uuid` ที่ Postgres ยอมรับหลายสะกด → booking เดียวได้หลาย bucket (วัดได้ 5+5
  จาก IP เดียว, และ 20/20 ด้วยการสลับสะกด). ตอนนี้ handler **ปฏิเสธ 400 ก่อนเข้า limiter**
  ทุกสะกดที่ไม่ใช่ `gen_random_uuid()` form (lowercase มีขีด). **Codex ต้องไม่ผ่อน regex นี้**
  เพื่อ "รองรับ input ยืดหยุ่น" — ความยืดหยุ่นนั้นคือช่องโหว่นี้
- **F2 (MEDIUM) — fail-closed ใน planner:** ดูข้อผูกพันใน §4 (facts ขาดคีย์/ค่า grant อ่านไม่ได้ → โยน error)
- **F4 (LOW) — อย่าให้คนที่รู้แค่ bookingId เผางบลูกค้า:** งบต่อ booking ถูก "จอง" ก่อนเรียก runtime
  และ "คืน" เมื่อ RPC ปฏิเสธ token (หรือเมื่อ storage ล้ม) — งบต่อ source ไม่คืน เพื่อไม่ให้ attacker ได้เปล่า
  **ห้ามเปลี่ยนกลับเป็น "หักทุกครั้งก่อนตรวจ token"**
- **F5 (LOW) — ข้อความ 429 ต้องบอกชั้นที่ปฏิเสธ:** response มี `scope: 'booking' | 'source'`
  **ห้ามยุบกลับเป็นข้อความเดียว** เพราะผู้ใช้จัดการคนละวิธี
- **F3 (MEDIUM/HOLD) — ไม่ได้แก้ในรอบนี้:** ตัวนับยังเป็น in-memory ต่อ Worker isolate
  (`wrangler.jsonc` ยังไม่มี Cloudflare rate-limit rule) — งาน edge/platform ไม่ใช่ app

## 6. สิ่งที่ผู้เขียนไม่รู้ (ระบุตรง ๆ)

- ไม่ได้รัน SQL ใด ๆ กับฐานจริง — ข้อ R1–R4 เป็นข้อเสนอจากการอ่าน source เท่านั้น
- ไม่ทราบว่ามี House-side scheduler/retention อยู่แล้วหรือไม่ (House-owned schema
  `wstera_platform_internal` อยู่นอกขอบเขตที่ผู้เขียนตรวจ)
- **ไม่ได้อ่าน DDL ของ `deposit_money_events` เอง** — ข้อเท็จจริงเรื่อง FK ไม่ cascade + trigger
  ห้ามแก้ มาจากผลตรวจโค้ดของผู้คุมใน A-27 (ไฟล์ P0 `…120000` ไม่อยู่ใน worktree นี้);
  Codex/House ต้องยืนยันกับ DDL จริงก่อนออกแบบ R3
- **ตัวเลข retention ไม่ได้มาจากผู้เขียน** — มาจาก A-27 (Owner 2026-10-02) และข้อ 3/6/7
  ยังรอทนาย/บัญชียืนยัน ⇒ ค่าทุกตัวต้องรับได้จาก config ไม่ hard-code
- **ตัวระบบรันอัตโนมัติยังไม่มีเลย** (ไม่มี anonymize, ไม่มี purge job, ไม่มี hold flag,
  ไม่มี tombstone) — สัญญานี้เป็นข้อเสนอหลังเปิดขาย ไม่ใช่สถานะปัจจุบัน
